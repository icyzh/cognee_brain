## Context
svc-auth issues opaque session tokens that every service validates with a network call back to svc-auth. That call sits on the hot path of every payment request and svc-auth has become a single point of failure. A leaked long-lived token also stays valid until someone notices and revokes it by hand.

## Decision
svc-auth issues signed JWT access tokens with a 15-minute expiry, plus a rotating refresh token stored server-side. Services verify the signature locally using the published key set. Signing keys rotate monthly. Sam Okafor owns the token format and rotation.

## Alternatives considered
- Keep opaque tokens and add a cache in front of svc-auth: less work, but the cache still has to be invalidated on revocation and the dependency remains.
- JWTs with a 24-hour expiry: fewer refreshes, but a stolen token would be valid for far too long for a payments API.

## Consequences
Token validation no longer needs svc-auth to be up. Revocation takes effect within 15 minutes at worst. Clients must handle refresh, and key rotation becomes an operational task for Platform.
