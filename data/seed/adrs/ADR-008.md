## Context
Merchants retry requests when they hit timeouts or the 429s introduced by ADR-006. Today a retried capture or refund can be processed twice, and the TCK-131 double refund showed how expensive duplicate writes are. We need retries to be safe regardless of the storage engine.

## Decision
Every write endpoint on svc-payments (authorise, capture, refund) requires an Idempotency-Key header. The key and the response are stored for 24 hours; a repeat request with the same key returns the stored response instead of executing again. A repeat with the same key but a different body is rejected with 422. Marco Rossi owns the implementation.

## Alternatives considered
- Deduplicate on request body hash: breaks for legitimate identical payments.
- Rely only on client SDKs to avoid retries: we do not control merchant integrations.

## Consequences
Retries become safe for merchants. It protects against duplicate requests but not against concurrent different requests on the same payment, which is a storage problem addressed separately. Merchants on old SDKs need to add the header before enforcement.
