## Context
On 2026-02-17 a compromised merchant API key was used to send thousands of card-testing authorisations per minute to svc-payments. Each service had its own ad-hoc limits, none of them tied to the API key, and the attack was only stopped by revoking the key manually.

## Decision
All public API traffic is rate-limited at the API gateway, per API key, using limits stored in svc-auth. Default limit is 100 requests per second per key, with lower limits on authorisation endpoints. Exceeding the limit returns 429 with a Retry-After header. Sam Okafor owns the limits.

## Alternatives considered
- Per-service limits in application code: already failed, inconsistent and hard to change quickly.
- A third-party bot-protection service: useful later, but slower to roll out than gateway rules.

## Consequences
Abuse is throttled before it reaches svc-payments. Large merchants may need raised limits, handled through svc-auth config. Client SDKs must respect Retry-After.
